# Visual PRD

生成原型与需求文档同屏展示的可视化 PRD。

## 资源与路径

- 将 `SKILL.md` 所在目录作为 Skill 根目录；从任意工作目录调用时，先把下列相对路径解析为该根目录下的绝对路径。
- 编辑保存、流程图和页面下载的实现与验收要求见 [编辑与导出指南](references/editing-and-export.md)。
- 生成 PRD 前读取 [PRD 模板](references/prd-template.md)。
- 设计锚点、标注数据与编号时读取 [标注指南](references/annotation-guide.md)。
- 实现 Markdown 文档区时读取 [Markdown 渲染指南](references/markdown-render-guide.md)。
- 处理第三方 HTML、跨工具分发或发布前安全审查时读取 [安全与可移植性边界](references/security-and-portability.md)。
- 基于 [原型骨架](assets/prototype-template.html) 生成原型，并注入 `scripts/prototype-runtime.js` 与 `scripts/annotation-runtime.js`。
- 使用 `assets/container-template.html` 装配最终容器；`assets/container-styles.css` 作为拆分开发时的基础样式参考，最终 HTML 仍须将资源内联。
- 迁移或交付 Skill 前运行 `python3 scripts/validate-package.py`，确认目录、模板占位符、离线资源、脚本语法、交互声明和烟雾构建完整。

## 工作流

### Phase 1: 需求接收与澄清

- 读取用户提供的需求描述、会议记录或产品想法
- 提出 3-5 个聚焦的澄清问题，围绕当前最缺的关键信息
- 根据复杂度进行 2-3 轮澄清
- 将澄清结果整理为产品定型文档

### Phase 2: PRD 板块规划

- 根据定型文档，输出板块计划（有哪些功能板块、优先级和依赖关系）
- 等待用户确认板块计划

### Phase 3: 逐板块生成 PRD + 原型

对每个板块依次执行：

#### 3.1 生成 PRD 文档

- 包含：功能描述、用户故事、业务规则、状态机、验收条件
- 额外生成 `flows.md`：业务流程、核心功能流程、实时数据流（不涉及的类型说明原因）。流程依据已确认业务规则，未知节点标注“待确认”；每张图必须配套文字描述，说明入口、角色、主要步骤、判断分支、异常/回退和最终结果；数据流图额外说明数据来源、传递方向、更新触发与失败处理。文字依据已确认需求，不明确的部分标“待确认”。用 Markdown 标题、文字说明和 `mermaid` 围栏代码块组织。编辑区必须显示可读的 `graph TD` / `flowchart` 等节点、连线与分支源码；预览用内嵌 Mermaid 库离线渲染 SVG。不得把流程图源码替换为 base64 图片数据。图片粘贴仍用于补充资料。

#### 3.2 生成原型页面

- 必须基于 `assets/prototype-template.html` 生成原型，不允许跳过 `prototype-runtime.js` 直接手写交互逻辑
- 引入 prototype-runtime.js
- 定义初始 state（包含该板块所有可变数据）
- 定义页面结构，可点击元素必须带 data-action
- 定义每个 action 对应的状态变化和跳转目标
- 所有交互必须有可见反馈（状态变化、页面切换、弹层开合、Toast 提示）

#### 3.3 交互自检（必须执行）

生成完成后，逐项检查以下清单，任何一项不通过则修复后重新检查：

先运行 `node scripts/check-interactions.js <原型 HTML 文件>`，检查所有交互点是否已绑定有效页面、弹层、状态或处理器。脚本报告存在未绑定交互点时，必须修复并重新运行，直至检查通过。

静态脚本通过不等于交互通过。随后必须在真实浏览器中逐项操作本清单，检查可见 DOM、路由、状态和控制台；不得只阅读源码或沿用旧报告。自检报告必须覆盖当前清单的每个分组，并记录测试对象、时间、实际结果和修复记录。

【导航类】

- [ ] 主导航每一项点击后能切换到对应页面
- [ ] 页面内“查看详情”“返回”等按钮能正确跳转
- [ ] 浏览器前进/后退能正确切换页面

【切换类】

- [ ] Tab 点击后内容区正确切换
- [ ] 步骤条点击后能跳到对应步骤
- [ ] 开关/单选/多选点击后状态变化且视觉更新

【弹层类】

- [ ] 所有“新建”“编辑”“查看”按钮能打开对应弹层
- [ ] 弹层内“取消”“关闭”“确定”能正确关闭
- [ ] ESC 键和点击遮罩能关闭最顶层弹层

【表单类】

- [ ] 输入框输入后 state 同步更新
- [ ] 表单提交有反馈（成功 Toast 或错误提示）
- [ ] 必填项为空时显示校验错误

【列表类】

- [ ] 筛选条件切换后列表内容更新
- [ ] 搜索框输入后列表实时过滤
- [ ] 排序点击后列表顺序变化

【状态类】

- [ ] 空状态、加载状态、错误状态有对应展示
- [ ] 操作后相关数据区域自动重绘

【编号一致性】

- [ ] 每个标注的编号在原型圆点和右侧面板中完全一致
- [ ] 编号只来源于标注数据的 order 字段，没有第二处独立计算
- [ ] 同一时刻可见的标注编号从 1 开始连续，无跳号、无重号
- [ ] 跨页面标注进入页面基础序列，页面内标注顺延且不冲突；顶层弹层独立编号
- [ ] 运行时断言开启，控制台无编号不一致警告

【标注联动】

- [ ] 鼠标移入和移出标注圆点时位置稳定，不重复重绘或闪动
- [ ] 点击右侧标注条目后，中间原型自动打开相同 `data-anno` 的标注详情
- [ ] 右侧条目支持 Enter 和空格键打开对应标注

【Markdown 渲染完整性】

执行本分组前读取 [Markdown 渲染指南](references/markdown-render-guide.md)。

- [ ] 表格渲染为 HTML `<table>`，不是原始 Markdown 文本
- [ ] 标题层级正确，无跳级
- [ ] 列表渲染为 `<ol>`/`<ul>`
- [ ] 代码块渲染为 `<pre><code>`，且保留缩进
- [ ] 行内代码、加粗、斜体、引用块均正确渲染
- [ ] 表格前后有空行，不会因缺空行被解析为段落
- [ ] 测试文档实际包含以上每种语法；未覆盖的语法不得标记为通过

【编辑、持久化与开发交付】

- [ ] 每条标注的编辑按钮可改标题、正文和业务规则；编辑按钮不误触发原型交互
- [ ] 粘贴图片后，右侧卡片和原型标注详情一致；刷新保留文字和图片
- [ ] “授权自动写回”选择 HTML 后，后续输入自动写回同一文件；实际检查磁盘字节并以新路径/新浏览器上下文重开，不能仅检查 localStorage
- [ ] 保存状态区分草稿与磁盘写回，拒绝/取消授权、权限失效和写入失败不会报成功；未写回就关闭时提示
- [ ] 左右栏独立关闭/开启，原型画布填充空间，状态重开恢复
- [ ] 流程图在产品概述后，编辑为 Mermaid Markdown 源码、预览为图；文字说明和修改后的节点/连线写回 HTML 后可恢复
- [ ] 当前页下载以当前页面为入口；全部下载 ZIP 内页面数匹配全部原型页面（含未访问页）
- [ ] 解压并离线打开每个 HTML，验证导航、弹层、输入与提交；文件不含 PRD、评审标注数据、圆点和标注 runtime

输出自检报告，列出每一项的通过情况和修复记录。

### Phase 4: 装配与交付

- 将所有板块的产出装配为一份完整的单文件 HTML
- 从 Skill 根目录运行以下命令；所有尖括号参数均替换为实际文件路径：

```bash
python3 scripts/build-container.py \
  --prototype <prototype-source.html> \
  --prd <prd.md> \
  --annotations <annotations.json> \
  --flows <flows.md> \
  --prototype-output <prototype.html> \
  --output <visual-prd.html>
```

- 保留容器模板的逐条标注编辑按钮、顶部独立栏位开关和 ZIP 下载按钮、产品概述后的流程图章节、翻页右侧的当前页面下载按钮，以及“授权自动写回”入口。
- 在浏览器中预览，验证标注定位是否准确
- 导出为可离线打开的最终交付物
- 对最终交付物重新运行浏览器自检，确认没有外部资源请求、未处理异常或编号警告
- 迁移 Skill 时运行 `python3 scripts/package-skill.py`，不要手工压缩；脚本从 frontmatter 的 `metadata.version` 读取版本并生成平台中立的版本化压缩包，不包含平台专属元数据和宣传封面

## 重要原则

- 标注内容必须来自 PRD 或明确标记为"待确认"，不脑补业务规则
- 每个标注块按页面内容、交互说明、业务规则、字段说明、待确认组织
- 原型标注入口必须先显示区域序号，点击序号后再查看详情
- 每条标注必须显式定义 `order`；原型圆点和右侧面板只读取该字段，不得用数组索引临时计算编号
- 按当前可见交互视图从 1 连续编号；`pageId: "*"` 的跨页面标注进入页面基础序列，互斥 Tab 可复用同一序位，顶层弹层独立从 1 编号
- 标注 runtime、bundle 与页面 data-anno 锚点必须同时存在并能命中
- 构建期必须保证标注数据 ID 与原型 `data-anno` 一一对应；缺数据、缺锚点或重复锚点均视为失败
- 只把经检查的当前任务原型注入容器；未知或第三方 HTML 不得进入使用 `allow-same-origin` 的 iframe

## 故障处理协议

当用户报告任何可视化 PRD 的问题时，按以下协议执行，不需要用户分步引导：

1. 收到问题后，先输出一段简短的诊断（不超过 10 行）：
   - 涉及哪个模块
   - 最可能的根因
   - 准备修改哪些文件

2. 然后直接修复，修复原则：
   - 从源头改，不在渲染层打补丁
   - 保持单一数据源
   - 精确命中，不收窄范围不罢休

3. 修复后自动执行相关自检项，输出结果表

4. 任何一项不通过，继续修复直到全部通过，不需要用户再次提醒

常见问题的修复规则：

【编号不一致】编号只来自 order 字段，禁止任何位置用 index 计算；同一时刻可见的标注不得重号或跳号

【表格不渲染】确保渲染器启用 GFM 表格扩展，表格前后有空行

【点击误触发】handler 必须用 closest('.anno-dot') 校验，返回 null 直接 return

【标注内容对不上】内容必须来自 PRD 或标记为"待确认"，不脑补业务规则

【交互不生效】基于 prototype-runtime.js 的 data-action 机制实现，不允许手写独立交互逻辑
